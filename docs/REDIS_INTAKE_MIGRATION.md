# Явная миграция приёмника после отката Blob

Операция `migrate-redis` предназначена для одного перехода после успешно
завершённого `rollback-empty`. Она сохраняет прежние журналы, seed и checkpoint
в каноническом SSH-хранилище. Редакционная БД остаётся в Actions.

Подготовка кода не разрешает подключение нового сервиса. До рабочего запуска
нужно отдельное подтверждение владельцем точного назначения Upstash и передачи
токена бота и открытых черновиков в его закрытое хранилище. Ключи сервиса нельзя
передавать через аргументы команд, workflow inputs, журналы или артефакты CI.

## Условия первого запуска

1. В каноническом состоянии `ingress_rollback.phase=complete`, сохранён
   `completion_audit_sha256`, отсутствует `intake_state.ingress`, позиция
   `serverless_sequence` равна нулю. Обычный polling продолжает работать.
2. У рабочего бота отсутствует webhook. Проверены его имя и доступ к сообщениям
   основного канала.
3. Закрытый запрос `POST /api/transfer` с `operation=storage-info` подтверждает
   `backend=redis`, `namespace=production`, `initialized=false`. Это означает
   отсутствие обоих ключей config и state. Чужие или частично созданные данные
   перед первым запуском блокируют миграцию; автоматически их не очищают.
4. Точный SHA актуального main прошёл CI, включая Linux-тесты реального
   SSH-хранилища и проверку Redis CAS на отдельном временном Redis в CI.

После подтверждения назначения сервиса и готовности конфигурации оператор
запускает только ручной workflow `ingress-cutover.yml` на main с
`operation=migrate-redis`. Дополнительные параметры доказательства старого
`rollback-empty` для этой операции не используются. Все изменения состояния
выполняются под общей очередью `canonical-editorial-state`.

## Порядок переключения

Операция повторно проверяет пустой Redis, восстанавливает текущий проверенный
снимок SQLite только для чтения и создаёт свежий seed. Незавершённые или
неопределённые ответы читателям блокируют переключение.

Точный seed и журнал намерения сохраняются как неизменяемые объекты SSH.
Затем транзакция `ready → busy → ready` записывает обычный
`intake_state.ingress.phase=prepared` и отдельный `ingress_migration`. Этот
маркер связывает Redis, production namespace, URL, SHA seed, SHA исходного
снимка и журнал завершённого отката. С этого момента polling запрещён.

Перед bootstrap проверяется конфигурация Redis ещё раз. Bootstrap использует
сохранённый seed и должен подтвердить его SHA и рабочий режим. Повторная
проверка `storage-info` после bootstrap требует тот же seed и `mode=active`.
Только после этого вызывается `setWebhook` с `drop_pending_updates=false`,
`max_connections=1`, без изменения `allowed_updates`. После проверки Telegram
следующая транзакция переводит оба канонических маркера в `active`.

## Сбой и повтор

`migrate-redis` можно повторить при готовом каноническом состоянии и его
неизменном маркере миграции. Повтор читает прежний seed из SSH; новую дату,
новый seed и новый пустой transport поверх существующих данных не создаёт.

Для `prepared` допустим ещё пустой Redis либо частичный bootstrap с тем же
seed и `mode=incomplete`. Завершённый Redis допускается только с точным SHA
seed и `mode=active`. Для повторного `active` пустое или частичное хранилище
запрещено. Позиция уже импортированной очереди при таком повторе сохраняется.

При ошибке после захвата `busy` автоматического сброса нет. Нужно проверить
неизменяемый recovery checkpoint и применить существующую процедуру
восстановления канонического writer. При `prepared` polling остаётся
запрещённым до проверенного завершения миграции или отдельной процедуры
отката. Простое `activate` после прежнего отката по-прежнему запрещено.

Журналы операции содержат фазы, хеши и счётчики. Токены, тексты черновиков и
файловые идентификаторы читателей в них не выводятся.
