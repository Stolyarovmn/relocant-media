# SQLite для последовательной редакции

Этот адаптер совмещает текущие source policies, event-level дедупликацию,
пакетыv1/v2, очередь source_revision и устойчивые окна primary с SQLite.
PostgreSQL сохраняет прежние типы, миграции и блокировки. Тесты общей очереди
выполняются на обеих БД. Реальная публикация и перенос канонической БД пока
не включены; существующая PostgreSQL и квитанции сообщений8–11 остаются на месте.

## Файл и схема

Рабочий файл располагается локально рядом с единственным обработчиком.
Новая SQLite создаётся явной командой обслуживания:

```powershell
python -m relocant_media.ops.sqlite_schema_cli --database state/editorial.sqlite3
```

Каталог state должен существовать. Схема SQLite имеет user_version=1 и соответствует
текущему набору моделей, включая source_revision. Это отдельный номер схемы SQLite,
а не замена Alembic PostgreSQL. Обычный primary/экспорт/сбор проверяет существующий
файл, версию и целостность; не инициализирует пропавшую БД заново.

Для старого файла из PR36 сохраняется отдельный backup через SQLite Backup API;
добавляются политики, event fingerprints, версии правил, журнал ревизий и
контрольные точки. Старые ID, evidence, пакеты и квитанции не меняются. Неизвестная
схема или нарушение связей блокирует миграцию. Все DDL и номер версии фиксируются
в одной транзакции только после проверки целостности. Существующий backup не
перезаписывается. Все обработчики на время обслуживания должны быть остановлены.

**Старые даты требуют аудита.** SQLite мог потерять исходный offset при прежней
записи DateTime. При наличии старых дат миграция по умолчанию останавливается.
`--legacy-utc-confirmed` разрешён только после проверки, что все сохранённые даты
действительно UTC; это не автоматическая коррекция. Неизвестные локальные даты
нельзя просто пометить UTC. Новые записи приводятся к UTC при сохранении и
возвращаются с явным часовым поясом. Наивные входные даты отклоняются.

## Обработка и защита

После отдельного обслуживания используется явная настройка:

```powershell
$env:APP_ENV='staging'
$env:DATABASE_URL='sqlite:///state/editorial.sqlite3'
```

`BEGIN IMMEDIATE` резервирует единственного writer до чтения evidence. Проверки
вторичных документов работают без PostgreSQL JSONB contains. Между коммитами
primary удерживает отдельный файловый lock рядом с базой; Windows и Linux
поддерживаются. Другой процесс не обрабатывает тот же файл; после аварии/выхода
OS освобождает lock. Использовать один канонический путь к локальному файлу,
не копии и не сетевую/синхронизируемую папку. Копия lock-файла на другой машине
не создаёт распределённую блокировку.

Логика5+5+2, повтор того же окна после сбоя, сохранность receipt и блокировка
изменившихся источников остаются обязательными. Экспорт кандидатов и ревизий
использует согласованную read-only SQLite-транзакцию. Автоматический приём новой
редакции и отправка поправки по-прежнему не реализованы.

## Google Drive

Drive выбран как возможное хранилище **версий/резервных копий**, а не место
одновременной SQL-записи. Подготовка завершённого снимка:

```powershell
python -m relocant_media.ops.sqlite_backup_cli --database state/editorial.sqlite3 --output backups/NEW
```

SQLite Backup API включает зафиксированные данные WAL. Функция проверяет схему,
целостность и связи, затем создаёт SHA256-манифест. При ошибке готовый манифест не
создаётся; незавершённый снимок не загружается. Старый каталог не перезаписывается.
Для выгрузки в Drive сначала загружается файл под уникальным именем, затем его
манифест со ссылкой на возвращённый Drive file ID. Старые версии сохраняются.
Наличие одного файла без подтверждённого манифеста не означает готовую копию.

Коннектор Drive доступен для ручной агентской загрузки. Автономный Google Drive
API-доступ из GitHub пока не настроен; новая база в Drive ещё не размещалась.
Для схемы «скачать перед запуском → обработать → загрузить» дополнительно нужен
общий единственный writer для всех хостов и проверка поколения восстановленного
снимка. Локальный файловый lock этого не обеспечивает. Конфликт или недоступность
актуальной копии должны останавливать обработку, а не создавать пустую БД.

Перед переносом из PostgreSQL требуется отдельный проверяемый экспорт всех
связанных таблиц с сохранением канонических ID и квитанций; старые SQLite-артефакты
Actions нельзя молча назначать более свежими. Такая миграция и восстановление
через Drive пока не выполнены. Не сохранять токены, MTProto-сессии или credentials
в snapshot и не менять доступ к папке Drive на публичный.

Официальные основания: https://www.sqlite.org/backup.html,
https://www.sqlite.org/useovernet.html,
https://developers.google.com/workspace/drive/api/guides/manage-uploads .
