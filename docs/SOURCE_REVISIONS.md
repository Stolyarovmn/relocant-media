# Изменения уже проверенных источников

Сборщик не перезаписывает доказательства, на которых основано ревью. Если город
отредактировал статью, `capture_collected_batch` сохраняет точный новый снимок
в `source_revision`, связывая его с прежним `raw_item_id`. SHA256 включает source,
article ID, URL, заголовок, текст и дату (UTC). Уникальность пары raw ID / SHA256
исключает дубли при повторном сборе. Другая редакция сохраняется отдельно.

Если материал ещё не был отправлен, все редакционные результаты, ссылающиеся на
изменённый документ, включая вторичные доказательства события, переводятся в
`source_changed_requires_review`. Старое сырьё, пакет ревью, текст и квитанция
доставки сохраняются. Если старая версия уже была отправлена, её `EditorialRun`
и outcome больше не переписываются задним числом: это неизменяемая запись того,
что фактически было проверено и отправлено. Новая редакция источника живёт как
отдельная revision и может породить отдельный follow-up после свежего review.

Остальная пачка продолжает собираться в той же транзакции. Ошибка БД или другая
ошибка сбора по-прежнему откатывает пачку. Изменение источника является явным
редакционным ожиданием, а не сетевым сбоем. `review_required` в сводке — число
наблюдавшихся изменённых материалов в этом запуске, включая уже известные снимки;
это не число новых строк `source_revision`. Планировщик сохраняет этот счётчик в
деталях запуска и `source_review_required` в общей сводке.

Подготовка, импорт пакета, захват отправки и запись сырья сериализованы общей
транзакционной блокировкой города. Блокировка берётся до блокировок строк; для
нескольких городов используется сортированный порядок. Данные после ожидания
перечитываются. Зафиксированное до решения об отправке изменение блокирует её;
изменение после уже зафиксированного `sending` не отменяет отправку задним числом.
Внешний Telegram-вызов выполняется после фиксации квитанции, как и прежде.
Предпросмотр и отказ до захвата отправки удерживают блокировку до commit, rollback
или закрытия сессии вызывающим кодом. Для каждой операции требуется выделенная
короткоживущая сессия.

## Экспорт для повторного независимого ревью

Сначала требуется миграция `0008`; в обычном редакционном выпуске миграции не
выполняются. Затем с явно заданными `APP_ENV=staging` и `DATABASE_URL`:

```powershell
python -m relocant_media.ops.revisions_cli --city belgrade --output work/revisions-NEW
```

Экспорт читает БД в согласованной read-only транзакции и создаёт новый каталог.
Он содержит все сохранённые редакции без ограничения количества, старое сырьё
отдельно от новых доказательств, время наблюдения, SHA и текущие политики источника.
Сохраняется `approval=false`, `status=requires_fresh_review`. Исторические снимки
не выдаются за последнюю живую версию: перед новым ревью нужно открыть первоисточник.

## Control plane для решений по revision

После миграции `0010` решения о том, что делать с обнаруженным изменением,
фиксируются отдельно от evidence в append-only таблице `source_revision_decision`.
Разрешены только три управляющих решения:

- `queue_reverify` — создать свежий редакционный кандидат из точного revision snapshot;
- `hold` — удержать изменение до появления контекста или дополнительного доказательства;
- `superseded` — отметить конкретную revision как перекрытую более новой revision.

Каждая запись содержит `reason_code`, `actor`, необязательную заметку, время и
`idempotency_key`. Повтор того же управляющего вызова с тем же ключом идемпотентен;
использовать ключ для другого решения нельзя. История решений не перезаписывается.

Миграция `0013` добавляет `source_revision_materialization`. При `queue_reverify`
создаётся ровно один новый `RawItem` с отдельным ID и неизменяемой lineage:
`revision_id -> raw_item_id -> parent_raw_item_id`. Публичный URL остаётся точным
URL первоисточника; для внутреннего dedup используется versioned canonical identity,
чтобы изменённый заголовок/текст не был ошибочно отброшен как старая уже
рассмотренная версия. Старый `RawItem`, старый `EditorialRun`, post и delivery
receipt не переиспользуются новым review.

Явная запись решения выполняется отдельной командой с обязательным подтверждением:

```powershell
relocant-revision-control `
  --revision-id 17 `
  --decision queue_reverify `
  --reason-code material_source_change `
  --actor editorial-agent `
  --idempotency-key revision-17-reverify `
  --confirm-write
```

Команда не вызывает Telegram и не публикует материал. Для `queue_reverify` она
может создать новый raw-кандидат, который затем проходит обычный полный редакционный
pipeline как новый материал. Само управляющее решение не является одобрением
публикации и не снимает требования свежего review. В общем
`relocant-newsroom --database` секция `source_revision_control` показывает историю
решений, `materialized_raw_item_id` и факт создания свежего кандидата.

Критический инвариант: **старое одобрение никогда не переносится на revision**.
Новый кандидат должен заново пройти rank/claims/verify/draft и все действующие
source/factual/audience/delivery guards. Если revision только удержана или помечена
`superseded`, новый кандидат не создаётся. `superseded` не является фактическим
опровержением или автоматическим принятием новой версии — это только управляющая
запись в журнале.

Для lifecycle новая версия считается `source_update`. Связь с родителем доступна
через `source_revision_lifecycle_context`: сохраняются parent/raw IDs, parent/new
`event_key`, revision SHA и наличие свежего `EditorialRun`. Это позволяет в следующих
слоях различать перенос, отмену, смену площадки/цены и другие follow-up изменения,
не пытаясь угадывать их по одному заголовку.

Маршрутизация Gemini primary → ChatGPT fallback, рекламные бюджеты и политики риска
не изменяются. Внутренняя функция `upsert_raw_items` по-прежнему строго отклоняет
изменение проверенного сырья; штатный сбор сохраняет revision snapshot, а новый ID
создаётся только контролируемым `queue_reverify` с явной lineage.
