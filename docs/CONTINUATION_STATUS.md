## Что блокирует включение

1. Настроить приватное хранилище контрольного указателя: существующий private repo,
   variable `EDITORIAL_STATE_REPOSITORY=owner/name`, scoped secret
   `EDITORIAL_STATE_TOKEN` с Contents read/write только для него. Runtime и bootstrap
   поддерживают этот вариант; публичный репозиторий кода и Actions остаются прежними.
   Это не вторая БД/очередь: каноническая SQLite по-прежнему одна в закрытом Drive.
2. Настроить runner-авторизацию Drive через защищённую настройку, разрешить чтение
   финального snapshot и запись в закрытую папку. `DRIVE_CREDENTIALS_JSON`/
   `DRIVE_STATE_FOLDER_ID` — действующие интерфейсы; секреты не передавать в чат.
3. Установить фактического старого писателя, дождаться завершения активной работы,
   остановить и запретить повторный запуск editorial/intake/deploy timers/services
   и остальных писателей. Проверить отсутствие параллельного getUpdates consumer.
4. Обновить единственную каноническую БД до нужной схемы штатной процедурой под lock,
   сохранив backup, Telegram IDs/offsets и sent/sending/uncertain. Создать свежий
   финальный snapshot после fencing, проверить Drive readback и восстановление.
5. Bootstrap выполнить только после выполненных предыдущих шагов. Затем preview,
   проверка опубликованной проекции, штатные cutover flags и отдельная проверка
   Telegram credentials/настроек. Не включать отправки ради инженерного теста.
6. Для облачного кандидата использовать существующий `mode=discovery`; после
   реального разрешённого прогона сверить каноническую `last_discovery` квитанцию.
   Dispatch/exit code сами по себе не доказывают принятие или публикацию.
