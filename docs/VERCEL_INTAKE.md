# Быстрая предложка на Vercel

Владелец18ноября2026 выбрал Vercel, пока Telegram Serverless ожидает доступа.
Это отдельный входной обработчик. Отбор, источники, модели, два ревью, каноническая
SQLite, публикация и итоговые ответы редакции остаются в GitHub Actions.

## Размещение и доступ

- Проект: `cosmoshooter/relocant-reader-intake`.
- Production origin: `https://relocant-reader-intake.vercel.app`.
- Хранилище: `relocant-intake-private`, режим `private`, регион `fra1`.
- Preview использует свой namespace по deployment ID. У production свой namespace.
  Preview не выполняет реальные вызовы Bot API, даже если bootstrap содержит active.
- В `/api/health` только имя сервиса, окружение и наличие конфигурации; обращений нет.
- Все операции `/api/transfer` требуют отдельный bearer `INGRESS_BRIDGE_TOKEN`.
- Telegram webhook проверяет секрет заголовка, ограничивает размер тела, сохраняет
  входящее и намерение отправки в private Blob до подтверждения пользователю.

На этапе подготовки автоматическая проверка отклонила запись новых секретов:
нужно явное разрешение точных мест передачи. До разрешения не запускать секретный
setup, bootstrap рабочего бота или `activate`. Авторизация Vercel и создание
закрытого хранилища выполнены отдельно; это ещё не подключение рабочего Telegram.

## Что потребуется подтвердить при подключении

1. Новый ключ связи: `INGRESS_BRIDGE_TOKEN` в preview/production проекта Vercel
   и то же значение как `EDITORIAL_INGRESS_TOKEN` в secrets репозитория
   `Stolyarovmn/relocant-media`.
2. Новый секрет webhook: `EDITORIAL_INGRESS_WEBHOOK_SECRET` в GitHub; при bootstrap
   он передаётся в закрытый конфиг приёмника Vercel.
3. Существующий `TELEGRAM_BOT_TOKEN` читается только рабочим Actions workflow и
   передаётся по аутентифицированному HTTPS в private конфиг этого приёмника.
   Личный MTProto не используется. Токен не выводится, не попадает в Git/preview
   и не передаётся в модели.
4. Переключение webhook на `/api/telegram` с одной линией доставки, без сброса
   ожидающих обновлений. Канонические черновики и старые кнопки сохраняются.

Локальный помощник настройки новых ключей `work/configure_vercel_ingress.py`
хранит свою восстановимую конфигурацию только в защищённом Windows DPAPI файле
в локальном каталоге outputs проекта. Он не читает существующий токен бота.
После первоначального отказа автоматической проверки владелец явно разрешил
перечисленные выше назначения. Настройка служебных ключей выполнена с этим разрешением;
значения не выводятся и не сохраняются в репозитории.

## Переключение

`ingress-cutover.yml` допускает только ручной запуск main с успешным CI на том же
коммите. Его очередь совпадает с единственным исполнителем канонического состояния.
Операция `preflight` читает снимок и проверяет принадлежность бота/права DM;
не изменяет webhook или указатель и не передаёт токен Vercel.

`activate` сохраняет точный приватный seed, затем записывает `ingress.phase=prepared`.
Так прежний polling уже заблокирован до включения webhook. Bootstrap получает
строку seed и её SHA256, конфигурация Vercel сохраняет только служебные параметры
и токены. Полного seed или архива заявок в неизменяемом конфиге нет.
После `setWebhook` и `getWebhookInfo` marker меняется на `active`. При сбое
остаётся подготовленное состояние; повтор использует тот же seed. Busy canonical
никогда не сбрасывается автоматически. Обе записи metadata используют штатный
переход ready→busy→ready; до каждого захвата сохраняется recovery checkpoint.
Прямая запись ready→ready запрещена протоколом хранилища. Восстановление допускает
этот workflow только после проверки завершённого ручного запуска main с точным
совпадением run ID и attempt.

Перед переносом незавершённые Telegram receipts и неясные отправки инструкций
требуют отдельной проверки. Простой возраст не разрешает их переотправить.

## Хранение и удаление

В Vercel хранится транспортная копия, а также ещё открытые choosing/collecting
черновики. Файлы Telegram не скачиваются; передаются их закрытые идентификаторы.
Actions импортирует события последовательно с проверкой user/chat/topic/reference.
Старая редакционная inline-кнопка передаётся текущему каноническому обработчику.

После проверенного сохранения SQLite и CAS состояния в `ready` Actions отправляет
ACK с курсором и хешем канонического снимка. Только тогда из Vercel удаляются
переданные события, тексты и закрытые черновики. Открытые черновики остаются.
Минимальные номера updates/хеши защищают от повторов в окне25часов;
просроченные квитанции очищаются при следующем изменении состояния.
Если ACK не дошёл, копии остаются и очистка повторяется после следующего снимка.
Ошибка очистки не откатывает уже сохранённую каноническую заявку.

Если результат отправки Telegram неизвестен, он сохраняется как uncertain без
автоматического повтора. CAS и чтение Blob без CDN-кеша защищают параллельные
запросы. Пределы: входящее512KiB, ответ peek480KiB, транспортная очередь4MiB.
При переполнении ответ не подтверждается; никаких silent drops.

## Проверки

Сначала локальные заглушки и полный Linux CI. Они покрывают оба входа, фото/видео,
редактирование нескольких сообщений, раннее нажатие, повторы и неопределённую
отправку, сохранение курсора, принадлежность кнопок, старые черновики, очистку
после snapshot и гонку новых updates с ACK. Preview разворачивается до разрешения
секретов с отключённым рабочим Telegram.

После разрешённого подключения нужны реальные входящие в чат бота и DM канала,
замер времени первой инструкции/подтверждения и проверка последующей очистки
очереди. Локальный тест с заглушкой не считается таким замером.
