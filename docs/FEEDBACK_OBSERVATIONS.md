# Наблюдения и контроль выпуска

После нормального серверного цикла `cycle-audit.json` сверяет сохранённые
тексты и фактические sent-квитанции: русский язык, обязательный префикс,
соответствие сообщения единственной записи БД, отсутствие ошибок обработки
и успешную проверку закрепов. Это не замена независимым редакционным ревью.
Относительные сроки в источнике привязываются к календарю Белграда: например,
19октября22:00UTC — уже20октября местного времени, и sutra означает21октября.
Автор и оба ревью получают это соответствие явно. В готовом посте требуется
абсолютная дата. Просроченное «завтра» отсекается до ИИ, а актуальное не удаляется
из-за другого UTC-дня. Неизменённый после замечаний черновик не отправляется
на повторные ревью ради другого результата: прежние замечания сохраняются.
Состояние `passed_no_publications` означает, что новых сообщений не было;
оно не выдаётся за проверенную новую публикацию. Вид Telegram сверяется отдельно.

`audience-observation.json` содержит фактическое число участников канала,
полученное через `getChatMemberCount`. Запрос не читает историю и не отправляет
сообщения. Bot API не даёт полной истории просмотров, поэтому недоступные
просмотры, реакции, комментарии и пересылки остаются `null`. Ошибка получения
показателей не должна превращаться в повторную отправку публикации.

Для приватного канала доступен снимок видимых счётчиков из авторизованного
интерфейса владельца. Он содержит только ID сообщений, момент наблюдения и
видимые показатели; неизвестные компоненты не заменяются нулями. Персональная
MTProto-сессия для этого не включается, публичность и права доступа не меняются.
При закрытом приложении сервер продолжает выпуск и сбор числа участников;
снятие просмотров через интерфейс тогда не работает.

`feedback_cli --observation <JSON> --metadata <JSON квитанций> --output <каталог>`
проверяет принадлежность сообщений нашему каналу и считает фактический возраст
по серверной дате публикации. Допуски:24±2,48±3,168±12часов. Наблюдение в другой
момент не превращается в историческое значение на отметке24часа. Исправленные
публикации сохраняются с отметкой и исключаются из исходного сопоставления.

Журнал JSON неизменяемый и идемпотентный. Он не импортируется в старую таблицу
PostSnapshot: та требует все четыре счётчика и могла бы превратить неизвестное
в нули. Рабочая SQLite остаётся канонической редакционной очередью; журнал
наблюдений не создаёт вторую очередь и не меняет sent-квитанции.

До30разных сопоставимых собственных публикаций — только накопление базы.
И после этого автоматическая адаптация не включается: нужны сопоставимые
варианты, минимум10наблюдений каждого, контроль качества и проверка устойчивости
вывода без самого успешного поста. Это технические минимумы, а не доказательство
статистической значимости. Нельзя обещать рекламный охват по двум подписчикам
и единичным просмотрам. Правила фактов и риска не обучаются по просмотрам.

Для расширения источников сначала проверяются свежая дата объявления, полный
текст и актуальная дата события. Пустая свежая лента не означает непопулярность
площадки. Кандидаты с неполным текстом не включаются ради увеличения счётчика;
результат проверки и причина остаются в event-discovery.json.

## Category learning

`relocant-category-learning` связывает уже сохранённые public-send квитанции с
`Post.category`, anchor source из `EditorialRun` и `PostSnapshot` на строго заданном
горизонте. Команда только читает БД и печатает JSON; она не меняет расписание
источников, редакционные пороги или публикации.

Пример:

```bash
relocant-category-learning \
  --city belgrade \
  --since 2026-10-01T00:00:00+02:00 \
  --until 2026-11-01T00:00:00+01:00 \
  --horizon-hours 24 \
  --minimum-samples 5
```

На один public post берётся не больше одного snapshot с точным `horizon_hours`;
если сохранено несколько снимков этого горизонта, используется самый поздний.
Пропущенные snapshots не восстанавливаются и не считаются нулевыми. Пост считается
публично отправленным только при `delivery_status=sent` и положительном
`telegram_message_id`.

Сравнение категорий начинается только когда минимум две категории набрали
`minimum-samples`. До этого рекомендация — продолжать сбор сопоставимых данных.
При зрелой базе категории сравниваются с наблюдаемой медианой по просмотрам на
пост и interactions/view. Это описательный сигнал, а не доказательство причинного
роста. Любой вывод о расширении или пересмотре discovery имеет класс `PR_REVIEW`.
`automatic_adaptation=false`: просмотры никогда автоматически не ослабляют
fact/evidence/relevance/high-risk guards и не включают `auto_publish`.
