# Точное исправление неподтверждённых утверждений

План версии 4 выполняется тем же ручным `editorial-correction.yml` только на
актуальном main с зелёным CI и общей блокировкой канонического состояния.
Он предназначен для удаления фактического брака из уже отправленного текстового
сообщения. Он не создаёт новое сообщение, не открывает закрытый lifecycle,
не меняет категорию, источник или разрешения публикации. Новая чувствительная
новость, призыв, смена темы, источник, медиа, карта или кнопки в этот путь не входят.
Протоколы исправлений v1–v3 сохраняют прежние ограничения.

План приватный. Реальные идентификаторы, тексты, документы и квитанции не попадают
в репозиторий. SHA всего файла передаётся единственным входом workflow. Внешний
загрузчик должен поддерживать v4; ранний загрузчик с whitelist v1/v3 этот файл
справедливо отклонит. Схема плана — `ExactTextCorrectionPlan` в
`relocant_media.ops.exact_text_correction`; размер всего файла ограничен прежними
32 КиБ. Типизированные поля запрещают дополнительные ключи, в частности новый
`category` или произвольный `chat_id`.

| Поля | Привязка |
|---|---|
| `version=4`, `operation=remove_unsupported_claims`, `city` | Единственная разрешённая область операции |
| `raw_item_id`, `post_id`, `message_id` | Один существующий Post и его настоящая sent-квитанция; канал задаётся кодом |
| `old_package_sha256` | Точный сохранённый проверенный исходный пакет v2 |
| `old_title_sha256`, `old_body_sha256`, `old_text_sha256` | SHA256 UTF-8 точных сохранённых строк и видимого Telegram-текста |
| `title`, `body`, `source_url` | Полный новый текст; исходная ссылка сохраняется, разметка строится штатным форматтером |
| `removed_fragments` | Точные удаляемые фрагменты исходного текста; в новой редакции они отсутствуют |
| `documents` | Весь исходный комплект документов, их JSON-хеши, хеши свежего видимого текста страниц и точные цитаты |
| `reviews` | Два свежих независимых одобрения точного контекста плана |

`document_sha256` — SHA256 `canonical_json` сохранённого `PackageEventDocument`.
`live_text_sha256` — SHA256 UTF-8 результата `source_text`: один распознанный
`article`/`main` без навигации, sidebar и служебных блоков, с нормализованными
пробелами. Для основной статьи N1 используются те же прямые блоки текста,
что и в действующем collector, вместе с единственным заголовком; отсутствие
или неоднозначность этих блоков блокирует операцию. Whole-DOM fallback отсутствует.
Цитаты непрерывны в этом
представлении и в нормализованном body исходного документа. Живое изменение
страницы, отключённый источник или изменение его политики блокирует операцию
до захвата состояния. HTML не становится инструкцией для исполнителя.

Оба ревью имеют разные идентификаторы и роли `facts`/`utility`, `approve`, score≥75,
пустые flags, `live_source_checked=true`, возраст не более двух часов и один
`context_sha256` от полного плана без `reviews`. Дополнительно каждый проверяющий
подтверждает `scope=remove_unsupported_claims_only`, `factual_support=supported`,
`no_new_sensitive_claims=true` и поясняет своё решение. Это локальные аттестации
проверяющих, как в существующем механизме исправлений; файл сам не запускает модели.

Проверяющий фактов заново сверяет весь новый заголовок и текст, включая выводы
о последствиях, с источниками и исходной публикацией. Отсутствие подтверждений
последствия не доказывает обратного: удаление неподтверждённого обещания не даёт
права утверждать, что последствие исключено. Проверяющий полезности независимо
оценивает ясность исправления и отсутствие новой темы, призывов или чувствительных
утверждений. Код проверяет формальные связи и область операции; он не доказывает
смысловую эквивалентность текста анализом ключевых слов. Два старых одобрения
ошибочного исходного пакета не заменяют эти два новых ревью.

До edit исполнитель проверяет readonly-снимок, старый публичный текст и живые
источники. Неизменяемое намерение и безопасная контрольная точка создаются до
CAS `ready→busy`. Только подтверждённый CAS и его readback разрешают один
`editMessageText`; HTTP retry отсутствует.
Оригинальные Post, пакет, доказательства и sent-квитанция не переписываются.
Отдельный приватный `exact_text_corrections` в каноническом указателе связывает
сообщение, план, намерение, отпечатки и квитанцию. Неизменяемые audit blobs содержат
историю проверки, API и публичного readback. В stdout — только статусы и хеши.
После подтверждённого API и публичного readback в копию исходного SQLite
добавляется `_published_correction` с точным приватным планом и связями всех
квитанций. Создаётся новый проверенный snapshot; его указатель фиксируется тем же
CAS. Read-only `effective_published_text` проверяет old hashes, исходный пакет,
receipt/intent/plan SHA и новые одобрения. `recent_publications` и newsroom читают
эту эффективную редакцию, сохраняя исходный Post как историю. Повреждённый overlay
не выдаётся за подтверждённое исправление. При `uncertain` confirmed overlay не
создаётся и исходный snapshot сохраняется.

Успех требует одновременно точного ответа Bot API о получателе/тексте/разметке
и независимого публичного readback. Timeout, иной получатель, неверная разметка,
устаревший публичный preview или недоступность readback означают `uncertain`.
Финальный CAS возвращает общий указатель в ready, но сохраняет запрет нового edit
для этого сообщения. Replay того же плана не отправляет запрос снова; другой
план также не обходит этот запрет. Подтверждённый исправленный текст при replay
сверяется публично и возвращает `already_corrected` без edit.

При падении после claim указатель остаётся busy. Контрольная точка разрешает только
явное штатное восстановление в `uncertain`, никогда автоматическую отправку.
После успешного snapshot/readback сохраняется отдельная финальная контрольная
точка с уже подтверждённой редакцией до финального CAS. Её явное восстановление
после сбоя commit тоже не повторяет edit.
Неизвестный результат CAS не повторяется. Для снятия неопределённости нужна
отдельная ручная сверка; времени или нового запуска недостаточно. Журнал ограничен
256 сообщениями и не удаляет историю автоматически при заполнении.
