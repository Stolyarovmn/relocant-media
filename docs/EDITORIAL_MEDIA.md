# Иллюстрированные редакционные выпуски

Для события сначала ищите материалы организатора и проверяйте место, год,
автора и условия использования. Доступная статья не подтверждает разрешение
скачать её фотографии для своего альбома. Ссылка и собственный краткий пересказ
не требуют превращать фотографии в наши вложения. Цитирование оценивается по
применимому праву и цели, а не по универсальному проценту материала.
Если происхождение или основание использования изображения не подтверждено,
оставьте ссылку на оригинал либо подготовьте собственную информационную карточку.
Не выдавайте иллюстрацию или архив за репортаж с текущего события.

`MediaRelease` связывает исходный raw item/post, канонический SHA256 редакционного
пакета, точную подпись, получателя и 1–10 локальных PNG/JPEG. Каждое изображение
имеет SHA256, происхождение, основание прав, подтверждение и атрибуцию. Для фото
нужен подтверждённый год и явная подпись с годом; атрибуция включается в caption.
Булево подтверждение прав — свидетельство редакционной проверки, а не автоматический
юридический вывод из наличия URL. Не выставляйте его без основания.

Два независимых медиа-ревью проверяют факты и полезность готовых изображений
вместе с подписью. Аттестация содержит хэши каждого файла, caption и всего контекста
без reviews (UTF-8 canonical JSON, ensure_ascii=false, sorted keys, separators=(',',':')).
Обе проверки действуют максимум 24 часа; текстовая редакционная политика проверяется
заново и сохраняет более короткие ограничения срочного исходного пакета.
Замена изображения, подписи, порядка, происхождения, прав или target требует
нового совпадающего контекста. Редактор не имитирует недоступного рецензента.

## Staging-проверка

По умолчанию команда проверяет реальные multipart-запросы через fake HTTP:

```sh
python -m relocant_media.ops.media_cli --release /run/release.json \
  --assets /run/images --receipts /persistent/staging-media-receipts
```

Требуются явно заданные `APP_ENV=staging`, `DATABASE_URL`, numeric
`TELEGRAM_STAGING_CHANNEL_ID` и `TELEGRAM_CHANNEL_ID` для исключения основного канала.
`.env`, AI-клиенты и MTProto не загружаются. Fake не расходует реальную квитанцию.
Только после отдельного разрешения владельца на конкретный тестовый выпуск:

```sh
python -m relocant_media.ops.media_cli --release /run/release.json \
  --assets /run/images --receipts /persistent/staging-media-receipts \
  --transport bot-api --send-staging
```

Проверенные байты передаются в HTTP без повторного чтения изменяемого файла.
Один снимок идёт через sendPhoto, 2–10 — через sendMediaGroup с подписью у первого.
Подпись ограничена 1024 единицами UTF-16; сообщения не дробятся с потерей смысла.

Квитанция staging-медиа хранится отдельно от исходного текстового EditorialRun.
Она эксклюзивно создаётся и синхронизируется на диск ДО HTTP: sending → sent или
uncertain. Успех сохраняет все message_ids. Повтор того же release_id и хэша
возвращает квитанцию без HTTP; другой контекст с тем же ID блокируется.
При sending/uncertain повтор запрещён до сверки фактического альбома. Не сбрасывайте
исходную квитанцию текста ради повторной публикации иллюстрированной версии.

Ограничение staging: все процессы должны использовать один устойчивый каталог
квитанций. Независимые хосты/каталоги не обеспечивают общую защиту от дублей;
для такого развёртывания нужен единый реестр доставки. Потеря каталога также
теряет гарантию повторов. Каталог и release_id нельзя менять ради обхода uncertain.

## Production delivery

Штатный `deliver_reviewed` теперь умеет выбрать иллюстрированный вариант внутри
той же DB-квитанции, которая защищает обычную публикацию от повторной отправки.
Это не отдельный второй publisher и не повторная публикация уже отправленного текста.

По умолчанию полностью проверенные production bundles ищутся в
`/var/lib/relocant-media/media-releases`; путь можно явно переопределить через
`EDITORIAL_MEDIA_RELEASE_DIR`. Структура одного выпуска:

```text
<media-root>/
└── <raw_item_id>/
    ├── release.json
    └── assets/
        ├── image-1.jpg
        └── image-2.png
```

Если каталога `<raw_item_id>` нет, редакция публикует обычный text-only пост.
Если каталог существует, но release, assets, права, два review, SHA256, caption,
post/raw identity, editorial package SHA или production target не совпадают,
весь выпуск блокируется до HTTP. Нельзя молча отбросить подозрительную картинку
и отправить текст, потому что это скрыло бы tamper/stale-review состояние.

Перед durable send claim заново выполняется стандартный editorial dry-run и затем
полная `MediaRelease`-проверка. Caption обязан быть точным текущим редакционным
текстом плюс требуемые attribution/archive labels. После claim Telegram получает
проверенные bytes через `sendPhoto` либо `sendMediaGroup`; произвольная загрузка по
URL в момент публикации отсутствует.

Для media-group первый Telegram message id остаётся каноническим `Post.telegram_message_id`
для существующих pin/analytics механизмов, а полный список message ids вместе с
release SHA и asset SHA сохраняется в `EditorialRun.outcome._media_delivery`.
Состояния используют ту же модель `sending → sent/uncertain`; неизвестный исход
Telegram-запроса никогда не приводит к автоматическому retry.

Production media integration сама не выставляет `rights_verified`, не создаёт
изображения и не превращает `og:image` в разрешённый asset. Поэтому отсутствие
доказанного безопасного изображения остаётся нормальным text-only результатом.

## Atomic production install

Готовый `MediaRelease` не надо вручную копировать в watched production directory.
Для установки есть отдельная команда без Telegram I/O:

```sh
APP_ENV=production relocant-media-install \
  --release /reviewed/release.json \
  --assets /reviewed/assets
```

Команда требует явный `DATABASE_URL`, сверяет release с текущими `EditorialRun` и
`Post`, повторно выполняет editorial dry-run, проверяет точный package SHA, caption,
production target, права, два media-review, имена и SHA256 всех assets. Каталог assets
должен содержать ровно те файлы, которые перечислены в release: дополнительные или
пропавшие файлы блокируют установку.

После проверки release и bytes сначала записываются и fsync-ятся во временный каталог
на том же filesystem. Только затем весь `<raw_item_id>` атомарно переименовывается в
production inbox. Существующий bundle никогда не перезаписывается. Ошибка до rename
удаляет staging-каталог и не оставляет частичный production bundle.

Установка допустима только пока исходный production run находится в `pending` и
у Post ещё нет Telegram receipt. Команда сама ничего не публикует и не меняет DB
статус доставки; штатный `deliver_reviewed` заново проверит bundle непосредственно
перед Telegram HTTP.
