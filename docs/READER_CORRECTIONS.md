# Читательские исправления

`/correction` остаётся частным сигналом редакции, а не доказательством и не командой
на изменение уже опубликованного сообщения. Сам текст обращения, Telegram user/chat ID
и вложения не публикуются в newsroom control plane и не становятся `RawItem`, claims или
evidence автоматически.

Существующий intake и triage продолжают использовать `Submission`: исправление получает
приоритет в закрытой очереди, может ждать первоисточник или быть связано с публичным
`raw_item_id`. Эта доработка намеренно не меняет `Submission.status`, чтобы не создавать
вторую очередь и не ломать текущий процесс проверки.

## Append-only решение

После миграции `0011` итог и промежуточные решения сохраняются отдельно в
`reader_correction_decision`. Разрешены только:

- `queue_verify` — требуется отдельная проверка по публичным доказательствам;
- `hold` — пока недостаточно контекста для вывода;
- `confirmed` — редакция независимо подтвердила наличие ошибки;
- `not_supported` — доступные публичные доказательства не подтверждают исправление;
- `superseded` — конкретное обращение перекрыто более новым исправлением/уточнением.

Каждая запись содержит `reason_code`, `actor`, необязательную заметку, время и
`idempotency_key`. История append-only: повтор того же вызова с тем же ключом
идемпотентен, а использовать ключ для другого решения нельзя.

`confirmed` означает только аудированный редакционный вывод. Он **не редактирует пост,
не удаляет сообщение, не публикует correction и не вызывает Telegram Bot API**. Реальное
публичное исправление должно идти отдельным delivery/corrections workflow с собственной
квитанцией и проверкой идемпотентности.

## Control plane

`relocant-newsroom --database` возвращает секцию `reader_correction_control`:

- число всех и нерешённых исправлений;
- intake status исходного `Submission`;
- связанные публичные `raw_item_id`, если они уже найдены;
- последнее решение, reason code, actor и число записей истории;
- сначала нерешённые обращения, внутри группы — самые свежие.

Приватный текст, Telegram user/chat ID и вложения в этот вывод не входят.

Явное решение записывается только с подтверждением записи:

```powershell
relocant-correction-control `
  --submission-id 42 `
  --decision confirmed `
  --reason-code official_source_confirms_error `
  --actor editorial-agent `
  --idempotency-key correction-42-confirmed `
  --confirm-write
```

Без `--confirm-write` БД не изменяется.

## Границы безопасности

- Частное сообщение не становится доказательством публикации.
- Audit decision не меняет `Submission.status` и не обходит обычный factual/source review.
- Никакого автоматического Telegram edit/delete/send в этом модуле нет.
- `not_supported` не означает, что читатель сознательно сообщил ложь; это только состояние
  доступных редакции проверяемых доказательств.
- Новое уточнение можно зарегистрировать отдельно; старую audit history не перезаписывать.
