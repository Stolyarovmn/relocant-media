# Устойчивая подготовка ограниченными пачками

`python -m relocant_media.ops.primary_cycle --city belgrade --output <новый каталог>`
запускает подготовку максимум пяти кандидатов через существующий Gemini CLI и
только fake Telegram transport. Это подготовка черновиков, не две независимые
редакционные проверки и не разрешение реальной публикации. Резервный подписочный
ChatGPT-процесс и его расписание не изменяются.

Состояние хранится в существующей PostgreSQL, в `scheduler_run`, с task key
`editorial-primary:belgrade`. Новая миграция не требуется; основная схема должна
быть обновлена до текущей версии отдельно от обычного выпуска. Артефакты GitHub
помогают диагностике, но не служат единственным хранилищем очереди.

Запуск атомарно сохраняет границы окна со статусом running до работы. При partial,
failed или аварийном завершении следующий запуск повторяет то же фиксированное
окно; уже сохранённые решения исключаются штатной event-level дедупликацией.
После обработки заново вычисляется остаток. PRIMARY_OK означает, что очередь
датированных кандидатов этого окна разобрана; PRIMARY_PARTIAL — хвост ещё есть.
Неполный проход не продвигает окно и завершает CLI ненулевым кодом.

После полного прохода следующее окно начинается с прежней верхней границы
с перекрытием десять минут. Если в БД уже обнаружен более старый необработанный
материал, нижняя граница расширяется до него. Так поздно найденная старая статья
не теряется из-за прежней контрольной точки. Начальный охват — сутки с таким же
расширением на имеющийся хвост. Публикации без даты остаются в БД, их число явно
указано в heartbeat; им не назначается дата сегодняшнего дня. Журнал source_revision
сохраняется отдельно и не считается одобренными кандидатами.

Сбор ограничен проверенными `city_beograd_news` и `cukarica_news`; остальные
адаптеры не включаются неявно. Сбой любого выбранного источника блокирует
обработку и продвижение окна. Изменения рассмотренных источников сохраняются
в журнале нового ревью и отражаются в счётчике review_required.

## База и блокировки

Требуется постоянная PostgreSQL с резервным копированием. Локальная staging-БД
55440 уже использует постоянный Docker-том; это не удалённая БД для GitHub.
В GitHub на момент проверки настроено имя секрета GEMINI_API_KEY, но нет
DATABASE_URL. До подключения постоянной БД workflow не является работающей
редакцией. Не создавать временную БД на каждый запуск и не считать исчезновение
истории новой успешной инициализацией. Потеря таблиц вызывает ошибку; восстановление
пустой БД из резервной копии требует отдельного операционного контроля.

Для primary требуется **прямое подключение или session pooling**. Transaction
pooling, включая соответствующие pooled URL PgBouncer, не подходит: session-level
advisory lock должен оставаться на одном серверном соединении между коммитами.
Пока worker работает, он держит отдельное соединение. Другой worker возвращает
PRIMARY_BUSY без обработки. Аварийное закрытие соединения освобождает блокировку;
обычное завершение явно снимает её до возврата соединения в пул. Для этого пути
пул должен допускать как минимум два соединения: блокировка и рабочая сессия.

Если основной проход активен, PRIMARY_BUSY не является поводом одновременно
запускать резервную обработку того же окна. Все процессы подготовки и отправки
по-прежнему соблюдают обычные редакционные guards и городские блокировки.

Workflow сохраняет исходное расписание `0 */3 * * *`,30-минутный предел и запрет
реальных отправок. Job включается переменной репозитория
`EDITORIAL_PRIMARY_ENABLED=true` после подключения и проверки постоянной БД.
Без неё job пропускается; пропущенный workflow не является PRIMARY_OK и не заменяет
heartbeat. Это позволяет принять исправление без запусков с отсутствующим DATABASE_URL.

Workflow сохраняет запрет
реальных Telegram/MTProto действий. Он больше не вычисляет окно по последнему
успешному GitHub workflow. Секреты и сообщения исключений API не попадают в журнал;
ошибки сохраняются только по типу. Реальная проверка Gemini API не выполнялась
инженерными тестами; тесты используют фиктивный обработчик и отдельную тестовую БД.
