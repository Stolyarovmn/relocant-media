# Дата публикации без выдуманного времени

`published_at_precision` сохраняется в CollectedRawItem, RawItem, evidence и
редакционном пакете: `day`, `instant` или `unknown`. Старые данные получают
`unknown`; миграция не делает исторические часы доказанными.

Официальные статьи Beograd с календарной датой получают `day`. Их прежний timestamp
хранится как нижняя граница местного дня для совместимости, а не как время публикации.
Границы вычисляются в Europe/Belgrade с учётом 23/25-часовых дней. Передаваемый модели
контекст показывает календарную дату и точность, а точное время для day/unknown равно
null. Публичная витрина не показывает выдуманные часы.

Выборка кандидатов включает пересечение календарного дня с окном и поздно найденные
датированные статьи текущего прохода. В manifest есть `window_match`; day никогда
не обозначается точным попаданием в трёхчасовой интервал. Существующий scheduler
также сохраняет незавершённый хвост и учитывает старейшие нерассмотренные материалы.
Freshness, event dedup, официальный первоисточник и high-risk guards не обходятся.

На границе 48 часов или семи дней неоднозначный day-интервал получает hold вместо
выдуманного точного возраста или преждевременного discard. Действующее исключение
для подтверждённого продолжающегося события сохраняется. Прямой официальный
материал с day/hold сохраняется для прозрачного triage, без вызовов модели.

Изменение precision является изменением evidence: импорт и доставка сверяют её,
наблюдение источника создаёт ревизию; прежние reviewed/sent данные не переписываются.
Старый пакет, чей контекст перестал совпадать после изменения модели данных,
требует штатного повторного ревью. Нельзя пересчитать подписи одобрений задним числом.

## Обновление единственной канонической БД

- PostgreSQL: Alembic `0015`, upgrade добавляет поле с default unknown, downgrade
  удаляет поле. Выполнять штатно, после резервной копии и остановки писателей.
- SQLite: schema v8. Штатный `sqlite_schema_cli` обновляет v7 только с резервной
  копией `.before-v8.backup`; старые записи сохраняются. Snapshot restore не мигрирует
  БД автоматически и отказывается активировать несовместимую схему.
- После согласованного обновления создать новый проверенный snapshot и выполнить
  обратное восстановление. Не обновлять production-БД во время инженерных тестов,
  не сбрасывать busy и не терять Telegram offsets/квитанции.
