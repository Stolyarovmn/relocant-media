# Модерация обсуждения

Модерация сообщений связанного обсуждения выполняется в существующем `TelegramRuntime`.
Это не отдельный Telegram-клиент и не MTProto-контур: решение принимает детерминированный
`services.moderation`, аудит сохраняется в `moderation_action`, а внешний side effect идёт
только через интерфейс `TelegramBot`.

## Решения v2

Каждое текстовое сообщение получает одно из трёх решений:

- `keep` — ни одно правило не сработало;
- `review` — есть неоднозначный сигнал, но данных недостаточно для безопасного удаления;
- `delete` — только высокоуверенный scam/spam сигнал.

В `reason` сохраняется стабильная строка `rules-v2:<reason_code,...>`; deterministic
правила не записываются как AI model.

### Автоматическое удаление

`delete` допускается только для узких сигналов:

- гарантированная прибыль/доход;
- `100%` доход/прибыль/заработок;
- сочетание дохода/инвестиций с утверждением «без риска»;
- явный призыв писать в личные сообщения именно ради заработка;
- одна и та же ссылка повторена в сообщении три и более раз.

Это high-confidence spam policy, а не общий классификатор рекламы или мнений.

### Только review

Неоднозначные сигналы никогда не удаляются автоматически:

- предложение написать в личные сообщения без high-confidence earnings scam;
- «быстрый заработок»/`easy money` без более сильного правила;
- пять и более ссылок;
- targeted harassment/threat phrase из узкого deterministic списка;
- сообщение длиннее 4000 нормализованных символов;
- переданные доверенным runtime rate hints: три повтора текста или восемь сообщений
  в наблюдаемом окне.

Rate hints являются входом `ModerationContext`; текущий Telegram runtime не выдумывает их,
поскольку в существующей схеме нет надёжной истории автора/текста для такого подсчёта.
Их можно подключить позже из отдельного проверенного агрегатора без изменения базовых правил.

## Идемпотентность

Telegram update уже защищён `telegram_update_receipt`. Дополнительно runtime перед новым
решением ищет существующий `moderation_action` по `telegram_chat_id + telegram_message_id`.
Если сообщение уже аудировано, возвращается прежнее решение и второй destructive API call не
выполняется. Это application-level защита, совместимая с историческими строками без новой
unique constraint/migration.

Решение сохраняется **до** `deleteMessage`. При сетевой неопределённости повтор того же
сообщения не создаёт второй delete: оператор видит сохранённое решение и может сверить
Telegram отдельно.

## Privacy и side effects

- personal MTProto session никогда не используется для модерации;
- сообщения вне явно настроенной discussion group игнорируются;
- `review` и `keep` не выполняют Telegram side effects;
- unit/integration tests используют fake `TelegramBot` и не обращаются к production Telegram;
- engineering task не запускает live moderation и не меняет production permissions/secrets.

## Проверки

Регрессии покрывают scam, benign phrase «без риска», подозрительную рекламу, harassment,
повторные/многочисленные ссылки, rate hints, обычную критику, audit reason codes, отсутствие
delete для `review` и отсутствие второго delete при другом update ID того же сообщения.
