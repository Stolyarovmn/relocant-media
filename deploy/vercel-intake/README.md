# Быстрый Telegram ingress

Node ESM, Node 24, закреплённый `@vercel/blob@2.9.0`. В этой директории только
ранний читательский диалог и надёжная передача обновлений в GitHub Actions.
Редакционные решения и каноническая БД остаются в Actions.

`npm ci --ignore-scripts` и `npm test` запускают проверки без внешних запросов.
Проверки SDK используют подставной адаптер; локальные тесты не читают `.env.local`.

## HTTP

- `GET /api/health`: публичные `service`, `mode`, `configured`. `configured`
  означает наличие переменных окружения, без чтения private Blob и без проверки
  завершённого bootstrap. Состояние bootstrap доступно только через `status`.
- `POST /api/telegram`: заголовок `X-Telegram-Bot-Api-Secret-Token`, до 512 КиБ.
  Ответ `200 {"status":"ready"}` выдаётся после надёжного сохранения события
  или проверки существующего receipt. При занятости/отказе хранилища — `503`:
  Telegram должен повторить запрос. Событие, которое целиком не помещается
  в экспорт до 480 КиБ, отклоняется с `413` без receipt и без отправки ответа.
- `POST /api/transfer`: `Authorization: Bearer <INGRESS_BRIDGE_TOKEN>`.
  Без настроенного bridge token все операции запрещены.

Операции передаются в JSON-поле `operation`:

```json
{"operation":"bootstrap","seed_json":"<исходный JSON снимка v1>","seed_sha256":"<SHA-256 точных UTF-8 bytes seed_json>","bot_token":"<из GitHub secret>","webhook_secret":"<новый секрет>","mode":"active"}
{"operation":"peek","after":0,"limit":30}
{"operation":"ack","through":12,"snapshot_sha256":"<SHA-256 сохранённого канонического checkpoint>","open_drafts":[]}
{"operation":"status"}
```

Bootstrap требует `seed.bot_id` с положительным целым ID бота, совпадающим
с префиксом токена. Вызывающая сторона заранее проверяет `getMe.id` и ожидаемый
username. Bootstrap идемпотентен для одинакового seed/секретов/режима и запрещает
замену другим seed. Повторный bootstrap не заменяет накопленные обновления.
Переменные `bot_token` и `webhook_secret` не передаются в ответах или логах.

`peek` возвращает `{status:"ready",events:[...]}` по возрастанию `sequence`,
только завершённые события. Ограничения — до 30 событий и до 480 КиБ сериализованного
ответа, поэтому клиент продолжает чтение с последней полученной последовательности.
Envelope: `{sequence,update,draft?,notice?}`. `draft.id` есть только у существующего
черновика из seed. В `notice` допустимы только итоговые `sent`/`uncertain`.
Все callbacks и неизвестные старые ответы передаются как неизменённый `update`
без `draft`. После старого `intake:` callback диалог этого участника передаётся
в Actions, чтобы локальный черновик не затёр канонический выбор.

`ack` вызывается **после** успешного канонического checkpoint, с его SHA-256.
Подтверждать можно только ранее выданные `peek` последовательности. События до
`through` и переданные принятые/отменённые заявки удаляются из mutable Blob;
открытые локальные черновики остаются. Обязательный для штатного клиента
`open_drafts` — полный список канонических `choosing`/`collecting` из сохранённого
checkpoint: `{reference,telegram_user_id,chat_id,topic_id}` без текста и вложений.
Он снимает существующий режим передачи диалога в Actions только после закрытия
его канонического черновика и подтверждения всех переданных обновлений.
Без поля `open_drafts` такой режим сохраняется. ACK не переводит собственные
локальные открытые черновики в этот режим.
Повтор ACK уже подтверждённого курсора идемпотентен при любом корректном SHA-256
нового канонического снимка: возвращает `ready`, не меняя сохранённый checkpoint,
черновики, ограничения диалогов или более свежие события. Первый ACK с курсором 0
подтверждает исходный снимок и может очистить ограничения из seed по `open_drafts`.
ACK не вызывает Bot API и не восстанавливает незавершённые отправки.

`status` отдаёт только `status`, `seed_sha256`, `mode`, `pending_count`,
`open_draft_count`, `busy`, `next_sequence`, `ack_sequence`, `can_send`.
`seed_sha256` служит маркером непрерывности с исходным снимком.

## Хранение и аварии

Все Blob закрытые. В production используются `production/config.json` и
`production/state.json`; preview использует отдельный префикс
`preview/<VERCEL_DEPLOYMENT_ID>/`. Неизменяемый config содержит только токены,
ID бота и SHA-256 seed — исходные заявки и seed JSON туда не записываются.
Mutable state хранит очередь, черновики, минимальные ограничения передачи
диалогов и receipts. Недрафтовые заявки из seed уже находятся в каноническом
checkpoint; их тексты и вложения сюда повторно не копируются.

Каждое чтение использует `get(access:'private',useCache:false)`, замена состояния —
`put(access:'private',allowOverwrite:true,ifMatch:etag)`. CDN-кэш не участвует
в принятии решений. Требование `max_connections:1` при регистрации webhook
снижает конкуренцию; CAS остаётся обязательным даже при этой настройке.

Перед `sendMessage` сохраняются исходный update, запланированный draft,
намерение отправки и уникальная попытка. Следующим CAS фиксируется `sending`.
После `maxDuration=30` секунд плюс 15 секунд запаса `sending` становится
`uncertain` и никогда автоматически не отправляется повторно. `prepared`
можно повторно захватить только по истечении этих 45 секунд. Восстановление
запускается следующим аутентифицированным webhook/peek-запросом, без таймеров
и фоновых процессов. Неопределённая отправка требует отдельного разбора.
`status` только читает счётчики, не восстанавливает отправку и не вызывает Bot API.

Максимум очереди — 4 МиБ, полного состояния — 8 МиБ, receipts — 30 тысяч.
Для завершения отправки заранее оставляется запас. При исчерпании места
новый update не получает receipt; обработка останавливается с `503` без потери
уже сохранённых событий. После ACK остаются только ID/hash/время/последовательность
обновления; receipts старше 25 часов очищаются при следующем изменении состояния.

Bot API ограничен `getChat`, `sendMessage`, `answerCallbackQuery`; callbacks
не подтверждаются преждевременным сообщением об успешном редакционном действии.
Перед ответом в личку канала проверяется `getChat.parent_chat.id`.
Вызовы Bot API разрешены только при `VERCEL_ENV=production` и `mode=active`.
Preview не вызывает даже `getChat`. Развёртывание, запись production-секретов,
bootstrap и переключение webhook выполняются отдельной процедурой cutover.

`.vercelignore` исключает локальные секреты, привязку CLI, зависимости, тесты
и локальные снимки из пакета развёртывания.
